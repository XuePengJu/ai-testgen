## 二、为什么要先做埋点

分层决策改造要动 ReAct 主循环，成本和风险都不低。动手前必须回答一个问题：  
**耗时到底花在哪？** 万一瓶颈在浏览器等待策略，换模型就是白干。

阶段 0 只加观测、不改逻辑，半天成本换一个确定答案。

## 三、埋点实现（已落地）

改动集中在 `app/services/explorer_agent.py`，新增约 70 行，**未触碰任何 ReAct 分支逻辑**：

## 四、四个关键发现

### 发现 1：瓶颈在决策层，占近八成

两个不同站点独立跑出 79.2% 和 81.5%，结论稳健。改造的理论收益上限约为总耗时的八成。

### 发现 2：95% 的步骤其实只是「短决策」

决策输出长度 p50 只有 95~117 字符——绝大多数步骤模型只输出 `{"tool":"browser_click","args":{"ref":"e4"}}` 这类短 JSON。  
样本 1 的 21 步里只有 1 步是 `submit_cases`（生成用例），样本 2 是 2 步。

也就是说：**真正需要生成能力的步骤不到 10%，剩下 90%+ 都是「从有限候选里选一个」的封闭判断。**  
这正好是 Choice/Noul 类原子判断的适用场景，拆分面覆盖绝大多数步骤。

### 发现 3：页面快照几乎免费（0.1%，约 3 ms）

`[e1] button 登录` 这种索引化元素表产出成本极低。  
意味着每步都可以放心喂全量候选元素，不必为省 token 做裁剪——这对「让模型从完整候选里选」是决定性利好。

### 发现 4（意外）：现有防重复护栏检测不到「震荡」

样本 1 第 10~18 步的真实轨迹：

```
navigate → /purchase-return/add → 404 → back → 列表页 → navigate → /add → 404 → back → ...
```

同一对动作来回震荡 5 次，白烧 5 步（约 10 秒 + token），但 `repeats` 计数为 **0**。

原因：现有防重复用 `action_key = f"{action}|{json.dumps(args)}"`，只在**连续相同动作**时累加；  
`navigate → back → navigate → back` 的 key 每次都不同，护栏完全失效。

样本 2 也有同类问题：单页官网的锚点被当成 URL，`browser_navigate` 触发了 19 次。

**这条比「快 3 秒」更有价值**——它暴露的是探索质量缺陷，不只是性能问题。阶段 2 应把防重复从「连续相同」升级为「状态去重」（访问过的 URL + 动作指纹集合）。

## 五、理论收益估算（待阶段 3 验证）

假设把 90% 的步骤从「通用模型 2141 ms」换成「决策层 ~300 ms」，仅 10% 生成步骤保留主模型：

```
改造后 ≈ 20 步 × 300 ms + 1 步 × 2141 ms + 浏览器 11.7 s ≈ 19.8 s
改造前 ≈ 56.8 s
→ 总耗时下降约 65%
```

这是**上界估算**，实际要打折：

- 小模型的准确率低于通用模型，低置信度步骤会回退主模型，产生额外开销
- 一次 chat 输出多字段 ≠ Jev 的多判断头并行，见下方差异说明
- 未计入新增的护栏判断（Noul）成本

阶段 3 用影子运行出真实数据后再定论。

## 六、Jev 与国产小模型复刻的差异（诚实版）

老板选型决策：先用国产小模型，Jev 作为可插拔 provider 留口子。两者的真实差距要说清楚：

| 维度   | Jev（TypeSafe）                      | 国产小模型复刻                              |
| ---- | ---------------------------------- | ------------------------------------ |
| 并行判断 | 模型层多判断头，一次前向传播返回多个原子结果，各自带**校准概率** | 一次 chat 输出一个多字段 JSON，可自评置信度但**校准性差** |
| 延迟   | 70~500 ms                          | 取决于模型，通常 300~1500 ms                 |
| 成本   | 输入 $0.042/百万 token，输出免费            | 按各家计费                                |
| 可用性  | 需 TypeSafe API key，国外服务，国内网络无保证    | 平台池已有，今日可用                           |
| 成熟度  | 2026-09-17 上 HN，社区 demo 为主，无生产验证   | 成熟稳定                                 |

**结论**：架构价值（分层 + 置信度降级）不依赖 Jev；Jev 只是把「延迟」和「概率校准」做到极致的一种实现。  
先用小模型把架构跑通并积累阈值数据，拿到 key 后换 provider，业务代码零改动。

## 七、阶段 1 / 2 设计草案（待拍板）

### 阶段 1：抽 `DecisionProvider` 接口

```python
class DecisionProvider:
    def choose(self, question: str, options: list[str], context: str) -> tuple[str | None, float]:
        """从有限候选中选一个，返回 (选中项, 置信度)"""
    def noul(self, statement: str, context: str) -> float:
        """判断陈述为真的概率"""
    def score(self, statement: str, context: str) -> float:
        """按预定义量表打分"""
```

两个实现：`SmallModelProvider`（默认，走模型池）、`JevProvider`（留口子）。  
不改主循环，先补单测。

### 阶段 2：改 ReAct 主循环

每步并行发三个原子判断，一次调用拿回：

1. **Choice**：下一步动作（click / fill / wait / snapshot / submit_cases / done）
2. **Choice**：目标元素 ref（仅 click / fill 时，从当前快照 ref 集合里选）
3. **Noul**：这一步是否危险 / 不可逆 → 补充现有关键词黑名单的语义盲区
4. **Score**：探索充分度 → 替代 `max_steps` 硬截断

置信度分诊：高 → 直接执行；低 → 升级主 LLM。  
`submit_cases`（生成用例）始终走主 LLM。

### 顺带修发现 4

防重复从「连续相同动作」升级为「访问状态去重」：`(url, action, args)` 指纹集合，命中即注入收敛警告。

# 阶段 1/2 实施与对照实验结果（2026-09-27 深夜追加）

分支 `feature/layered-decision`。代码：`app/services/decision_provider.py`（新增）+ `explorer_agent.py`（路由门控 + 震荡拦截 + 埋点扩展）。回归 407 passed（395 基线 + 12 新增）。

## 实施内容

1. **FastDecider**（决策中间层）：短 prompt（0.9KB vs 主 1.5KB）+ 封闭动作集（click/navigate/back/snapshot/screenshot/escalate）+ `enable_thinking=False`
2. **路由门控**（关键迭代）：首版"每步先快判、失败再升级"在首次对照中 10/12 步升级 → 每步白花一次快判调用。改为**主 LLM 决策时顺带输出 `next` 字段预测下一步类型**，下一步按预测路由——零额外调用
3. **震荡拦截**：`(url, action, args)` 指纹跨步去重，第 2 次警告、第 3 次硬拒（submit_cases 豁免）
4. **开关**：`EXPLORE_LAYERED=1` 启用，默认关闭，老行为不受影响

## 对照实验（erp.agentest.vip，admin 账密，三次独立运行）

| 指标 | 对照（分层关） | 实验 v2（路由，未关思考） | 实验 v3（路由+关思考） |
|---|---|---|---|
| 步数 | 12 | 15 | 15 |
| 总耗时 | **31.1 s** | 65.4 s | 56.4 s |
| 主 LLM 决策 avg | 2158 ms | 3173 ms | 2804 ms |
| 快判 avg / 接管率 | — | 2415 ms / 7÷15 | **2364 ms / 8÷15** |
| 升级次数 | — | 7 | 4 |
| 震荡拦截 | 0 | 0 | 1 |

## 诚实结论：速度假设被数据证伪

**1. 同池小模型快判不快。** 快判 avg 2364ms ≈ 主决策 2158ms。根因：耗时下限是**网络往返 + 服务端推理**（约 2 秒级），prompt 从 1.5KB 缩到 0.9KB 在 RTT 面前毫无意义；关 thinking 也没改善（该池默认无长思考）。

**2. Jev 的 70~500ms 来自专用低延迟推理端点，不来自「判断模型」这个概念本身。** 这是本次实验最值钱的发现——它把"为什么要 Jev"从概念问题变成了工程问题：**只有接入 RTT<500ms 的端点，分层架构才能兑现收益**。按 v3 接管率（8/15 步）估算，接入后每次探索可省约 8×1.9s≈15s，对照总耗时可降约一半。

**3. 路由门控与震荡拦截按设计工作。** 快判接管 8/15 步、升级仅 4 次（首版 10/12 的浪费已消除）、震荡拦截实战生效 1 次。

**4. 新的最大瓶颈浮出水面：浏览器等待（修正后约 31.5%）。** `BrowserSession.click` 后固定 `wait_for_load_state("networkidle", timeout=4000)`，SPA 下经常顶满 4 秒。这是下一个优化点，且与模型无关——换成 Jev 也救不了浏览器等待。
