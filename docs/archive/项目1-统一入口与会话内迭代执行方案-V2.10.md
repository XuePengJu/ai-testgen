## 1. 背景与问题

### 1.1 现象

任务详情抽屉 →「导出 / 迭代」Tab 中，除导出文件列表外，还包含一个完整的迭代输入区（textarea 补充要求 + 文件上传 + 取消/确认迭代按钮）。用户反馈：

> 为什么这里会有一个迭代按钮？下面又有一些输入框。我感觉它应该是在用例 Tab 里有一个按钮，引导用户回到主页会话里补充信息，而不是在这里再加一个按钮。

### 1.2 代码事实（只读排查结论）

| # | 事实                                                                                                          | 位置                                  |
| - | ----------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 1 | `ChatIn.task_id` 注释明确写「**迭代补充模式**：关联的任务 id，AI 回复时附该任务用例摘要」——设计意图本就是**会话内迭代**                              | `app/schemas/llm_config.py:56`      |
| 2 | 但聊天流只把旧任务摘要拼成 `context` 给模型**当参考**，不调用 `run_iterate`、不建 `parent_task_id` 链                                  | `app/api/chat.py:149`               |
| 3 | 前端发消息时**根本没有传 `task_id`**，该字段从未被启用                                                                          | `frontend/src/store/chatStore.ts`   |
| 4 | 真正的迭代是独立 API：`POST /tasks/{id}/iterate` → `run_iterate`（读父任务用例 → 导入合并去重 → 新子任务，版本链 + 版本号 v2/v3…）            | `app/api/tasks.py:232`              |
| 5 | `run_iterate` **结尾已实现**：「回填会话最后一条 assistant 消息的 task_id（聊天流回放时渲染节点卡）」——后端已预设迭代从会话发起，只差消息落库                  | `app/workflow/iterate.py:262-269`   |
| 6 | `iterate` 端点已接受 `conversation_id` 参数，默认继承 `parent.conversation_id`                                         | `app/api/tasks.py:240/275`          |
| 7 | 前端 `Task` 类型无 `conversation_id`（后端 `TaskOut` 不吐），详情页按钮无法定位所属会话                                              | `frontend/src/types.ts:87`          |

### 1.3 根因

**不是"不支持会话内迭代"，而是这条线当年只接了一半**：后端留了 `task_id` / `conversation_id` 两个口子并写好了回填逻辑，前端从未接上；迭代能力被临时安置在详情页表单里，造成"输入入口分裂"。

## 2. 目标与非目标

### 2.1 目标

| 编号  | 目标                                              | 衡量方式                                    |
| --- | ----------------------------------------------- | --------------------------------------- |
| G1  | **单一输入入口**：所有"发起工作"的输入都在主页会话输入框                 | 详情页输入控件数 = 0                            |
| G2  | **迭代能力不回退**：保留用例合并去重、`parent_task_id` 版本链、版本号递增 | 子任务 `source_type=iterate`、`name` 含 v(n+1) |
| G3  | **会话可回放**：迭代过程与结果在会话中以任务卡呈现                     | 会话内可见步骤进度 + 完成后「查看用例 / 思维导图」           |
| G4  | **意图无歧义**：不靠 LLM 猜"是不是迭代"                       | 由用户显式挂载迭代引用                             |

### 2.2 非目标（Non-goals）

- NG1：不在详情页保留任何输入表单（包括"轻量一行输入卡"）——用户明确要求不再开口子
- NG2：不改动 `run_iterate` 的用例合并算法、评审逻辑与导出格式
- NG3：不做多任务并行迭代（沿用现有 409 并发保护）
- NG4：不做会话内"引用历史消息 / 多版本对比"等扩展
- NG5：不让 LLM 自动判断迭代意图（易误判，本方案用显式引用）

## 3. 用户故事

- **US1**：作为测试工程师，我希望在会话里直接说"补充扫码登录的异常场景"，它是**基于上一个任务迭代**（继承原有 50 条用例）而不是从零生成，以便版本连续、用例不丢。
- **US2**：作为测试工程师，我在详情页看完用例后，希望有一个「继续优化」按钮把我带回会话，而不是在弹窗里再填一遍需求，以便只维护一个输入习惯。
- **US3**：作为测试工程师，我希望**清楚知道**"我这条消息会生成新任务还是迭代旧任务"，以便不误操作。
- **US4**：作为游客，我希望示例任务也能走这条路径迭代，以便体验完整闭环。

## 4. 方案设计

### 4.1 核心机制：迭代引用 chip

输入框上方新增一行**迭代引用 chip**：

```
┌──────────────────────────────────────────────────┐
│ 🔁 基于《采购入库管理 v2》迭代            ✕        │  ← chip
├──────────────────────────────────────────────────┤
│ 在这里描述你想补充的内容…                          │  ← 输入框
└──────────────────────────────────────────────────┘
```

规则：

| 状态    | 发送行为                                                                | 结果              |
| ----- | ------------------------------------------------------------------- | --------------- |
| 有 chip | `POST /tasks/{task_id}/iterate`（`instruction` + 可选 `file` + `conversation_id`） | 迭代子任务（合并旧用例 + 版本链） |
| 无 chip | 现有流程（`/chat/stream` → 生成测试用例）                                        | 全新任务            |

- chip 可通过 ✕ 一键取消 → 回到"新任务"模式
- 同一时刻只允许绑定一个迭代源，重新选择则覆盖
- chip 只在当前会话有效，切换会话自动清除（避免跨会话误迭代）

### 4.2 交互流程

```
① 详情页（任一 Tab）点「💬 继续优化」
      ↓
② 关闭抽屉 → 打开该任务所属会话 → 挂载 chip + 聚焦输入框
      ↓
③ 用户输入补充要求（可附加 xmind/xlsx/json 文件）
      ↓
④ 发送 → 走 iterate API（201 返回子任务空壳）
      ↓
⑤ 后台 run_iterate 执行 → 会话内出现任务卡（步骤进度实时更新）
      ↓
⑥ 完成 → assistant 消息回填 task_id → 任务卡变为「查看用例 / 思维导图」
      ↓
⑦ 点击「查看用例」→ 回到详情页看新版用例（v(n+1)）
```

### 4.3 详情页改造

- **删除**：「导出 / 迭代」Tab 中的整个迭代输入区（textarea、文件上传、取消/确认迭代按钮）
- **保留**：导出文件列表（该 Tab 职责收敛为纯"拿结果"）
- **新增**：「💬 继续优化（回到会话）」按钮 —— 位置待拍板（见 §11 决策点 1）

### 4.4 会话内任务卡

会话里已有的任务卡（assistant 消息带 `task_id`）上也挂「继续优化」按钮 → 直接挂载该任务的 chip，形成闭环，用户无需先开详情抽屉。

## 7. 影响分析

| 波及模块                    | 影响                          | 回归点                       |
| ----------------------- | --------------------------- | ------------------------- |
| 详情页迭代提交                 | 入口移除，改由会话发起                 | 需验证旧路径无残留引用               |
| 会话发送主流程                 | 增加分流分支                      | **必须验证无 chip 时行为与今天完全一致** |
| `run_iterate`           | 新增消息落库，不改合并逻辑               | 迭代结果正确性、版本号递增             |
| `TaskOut`               | 多一个字段（向后兼容）                 | 列表 / 详情接口无破坏              |
| 现有测试                    | `tests/test_guest.py`、`test_auth.py` 不涉及迭代 | 不受影响                      |
| e2e（Playwright）         | 若有迭代流程脚本，需改为走会话入口            | 需同步更新                     |

## 8. 验收标准（AC）

- **AC1**：详情页三个 Tab 内无任何输入控件（`textarea` / `input`），只有按钮
- **AC2**：点「继续优化」→ 抽屉关闭 → 会话打开 → chip 显示正确任务名（含版本号）→ 输入框自动聚焦
- **AC3**：带 chip 发送 → 后端收到 iterate 请求；DB 中新子任务 `parent_task_id = 原任务 id`、`source_type = iterate`、`name` 含 `v(n+1)`
- **AC4**：迭代完成后，会话中原位置出现任务卡（步骤 + 完成态），无需手动刷新；DB `messages` 中 assistant 消息 `task_id = 新子任务 id`
- **AC5**：无 chip 发送 → 行为与改动前完全一致（新任务）
- **AC6**：点 chip 的 ✕ → 恢复新任务模式
- **AC7**：chip 模式下仍可附加 xmind/xlsx/json 用例文件
- **AC8**：示例任务（`is_sample`）可正常迭代
- **AC9**：历史任务（`conversation_id` 为空）点「继续优化」不报错，按 §11 决策点 2 策略处理
- **AC10**：同一父任务并发迭代 → 409 提示以 toast 形式在会话中可见

| 风险                                       | 等级 | 对策                                       |
