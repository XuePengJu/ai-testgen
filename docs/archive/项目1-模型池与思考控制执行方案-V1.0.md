## 1. 实测：思考开关的真实代价与收益

### 1.1 方法

用项目 `.venv` 直连生产解析链（`resolve_effective` → `OpenAICompatClient._build_model`），
**输入全部取自真实任务 `b6d292a4903c` 的产物**（`uploads/u_1/b6d292a4903c.pages.md` + 38 条真实用例）。
只读探针，不写业务库。

- 模型：`Qwen/Qwen3.8-Flash-Next`（platform 默认，ModelScope 免费端点）
- 开关注入：`_build_model(..., enable_thinking=flag)`。**注意 `chat()` 目前不支持该参数**（见 §3.1）
- 思考字数取 `additional_kwargs.reasoning_content` 累加；正文字数取 `chunk.content` 累加

### 1.2 实验 A：脚本生成（8 条用例 → Playwright 代码）

| 档位 | 耗时 | 思考字数 | 正文字数 | 语法校验 | test_ 函数 |
|---|---|---|---|---|---|
| 关思考 + max_tokens 8192 | **61.4s** | 0 | 9847 | ✅ 通过 | 8 |
| 关思考 + max_tokens 32768 | **55.3s** | 0 | 10034 | ✅ 通过 | 8 |
| 开思考 + max_tokens 32768（**生产现状**） | **392.1s** | 72565 | 11418 | ✅ 通过 | 8 |

**结论**：关思考提速 **6.4~7.1 倍**；产出质量（语法合法性、函数数量）**完全一致**。
思考写了 7.2 万字，正文只比关思考多 1384 字 —— **思考基本是纯开销**。
生产 DB 记录的 375.3s/批与此处 392.1s 吻合，探针可信。

### 1.3 实验 B：探索 Agent 单步决策（max_tokens=2048，生产值）

| 档位 | 耗时 | 思考字数 | 正文字数 | 决策解析 |
|---|---|---|---|---|
| 关思考 | 1.9s | 0 | 155 | ✅ `browser_navigate` |
| 开思考 | 3.9s | 244 | 76 | ✅ `browser_snapshot` |

**结论**：这处差异很小（思考仅 244 字）。**原先"2048 预算会被思考挤爆"的担心未复现**。
两档决策都合理（一个直接跳转、一个先取快照）。**此处关/开皆可**，收益不显著。

### 1.4 实验 C/D：测试用例生成（3 个测试点 × 4 档位）

数据取自上一轮 44 分钟任务里**真实出现过 0 条的**那几个测试点。

| 测试点 | 关思考+8192 | 开思考+8192（**生产**） | 开思考+32768 | 关思考+2048 |
|---|---|---|---|---|
| 系统设置表单保存校验 | **8 条** / 28.9s | **1 条** / 113.7s | — | — |
| 采购订单创建入口验证 | 6 条 / 25.3s | 8 条 / 61.1s | 8 条 / 119.8s | 6 条 / 21.4s |
| 进销存核心模块入口验证 | **8 条** / 20.5s | **1 条** / 114.7s | 7 条 / 84.5s | 7 条 / 29.3s |
| **均值** | **7.3 条 / 24.9s** | **3.3 条 / 96.5s** | 7.5 条 / 102.2s | 6.5 条 / 25.4s |

**结论（最关键的一条）**：

> **开思考 + 8192（= 当前生产配置）是三个档位里产出最少、最不稳定的那个** ——
> 3 个测试点里有 **2 个只输出 1 条用例**，且耗时是关思考的 **3.9 倍**。

**机制推断**：开思考时模型把分析放进 reasoning，正文倾向于输出"摘要式"的少量结果
（不是 token 物理截断 —— 开思考的正文长度 3897/4075 字反而**比关思考的 2589/3496 字更长**）。
对"要求枚举 N 条结构化用例"的任务，这是灾难性的行为偏移。

**这直接解释了上一轮 44 分钟任务里 `12/8/0/0/7/8/0` 的产出形状**：
不是模型答不出，也不是纯解析失败，而是**开思考让部分测试点的正文退化成 0~1 条**。

### 1.5 三条硬结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **关思考快 4~7 倍** | 用例生成 24.9s vs 96.5s；脚本生成 55s vs 392s |
| 2 | **关思考产出更稳** | 关思考 5 次全部 6~8 条；开思考+8192 三次里两次仅 1 条 |
| 3 | **思考在本项目里几乎不创造价值** | 脚本生成思考 7.2 万字 → 正文只多 1384 字；产出结构完全一致 |

> ⚠️ **纠正上一轮的一处错误结论**：上一轮我据单次采样说"关思考代价是用例数 -25%（8→6 条）"。
> 本次 5 次关思考 + 3 次开思考的对照推翻了它 —— **真实情况是关思考产出更多、更稳定**。
> 那个 -25% 是采样噪声。

## 3. 关思考的实现方案

### 3.1 现状约束（重要，决定改法）

```python
# app/services/langchain_client.py
def chat(self, messages, temperature=0.3, max_tokens=8192, timeout=_TIMEOUT) -> str:
    for chunk in self._build_model(temperature, max_tokens, timeout).stream(messages):
        #                                       ↑ 第 4 参是 enable_thinking，但没接
```

- `chat()` / `generate()` **根本没有 `enable_thinking` 形参** → 调用点"想传也传不了"
- 只有 `chat_stream()` 支持（对话链路专用）
- `_build_model()` 本身支持，且有「端点不认该参数 → 400 自动去掉重试一次 + 记入 `_NO_THINKING_PARAM`」的兼容层
- 两套实现都要改：`LangChainClient`（默认后端）与 `_HttpxCompatClient`（`AITF_LLM_BACKEND=httpx` 应急）

### 3.2 两种改法

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）默认关** | `chat()`/`generate()` 新增 `enable_thinking: bool \| None = False`，默认即关；`describe_image` 显式传 `None`；对话走 `chat_stream` 不受影响 | **调用点零改动**，不可能漏改；语义正确（`chat()` 的消费方全是结构化任务） | 隐式默认变更，需在 docstring 与 PRD 里写明 |
| B 逐个显式传 | 默认保持 `None`，§2 表里 10 处调用点逐个传 `False` | 改动显式、可审计 | 10 处 × 2 类调用（`chat`/`generate`）= 易漏改；新增调用点仍会忘 |

**推荐 A**。理由：本项目里 `chat()`/`generate()` 的**全部消费方**都是结构化输出任务，
"默认不思考"才是正确默认值；而唯一需要思考的对话链路走的是另一个方法，天然隔离。

### 3.3 改动清单（方案 A）

| 文件 | 改动 | 说明 |
|---|---|---|
| `app/services/langchain_client.py` | `LangChainClient.chat()` 加参数并透传给 `_build_model`；`generate()` 同步透传 | 主实现 |
| 同上 | `_HttpxCompatClient.chat()` / `generate()` 同步 | 应急后端保持一致 |
| 同上 | `describe_image()` 显式 `enable_thinking=None` | 视觉槽保持"不注入" |

## 4. 多模型池设计（A 方案 · 按老板拍板细化）

### 4.1 拍板记录

| 决策项 | 结论 |
|---|---|
| 池化范围 | **不做优先级区分**，三个槽各自成池：`text` / `vision` / `embedding`，**每槽可加多条** |
| 数据模型 | **方案 A：新增 `llm_model_pool` 表**，`llm_configs` 一行不动 |
| 付费模型 | **允许**。池内模型一律使用**用户自己配置的 API Key**，费用由使用者承担；平台不代付 |
| 思考开关 | 另行评估（= 本方案 §1–§3） |

### 4.2 数据模型：新增 `llm_model_pool`

不做 DDL 改老表的依据：`init_db()` 走 `Base.metadata.create_all()`，**新表零迁移成本**；
且 `llm_configs` 上现有的 `scalar_one_or_none()` 查询（`resolve_embedding` 等）在同一 `(user_id, slot)`
出现多行时会抛 `MultipleResultsFound`，改它牵连面大。（方案 B/C 已在上轮评估中否决）

```python
class LLMModelPool(Base):
    __tablename__ = "llm_model_pool"
    __table_args__ = (
        # 重复配置校验：base_url + model + Key 指纹（+ 归属 + 槽位）全同才算重复
        UniqueConstraint("user_id", "slot", "base_url", "model", "key_fingerprint",
                         name="uq_pool_dedup"),
    )

    id              = Integer, primary_key, autoincrement
    user_id         = Integer, index       # 0 = 平台默认池（与 llm_configs 同约定）
    slot            = String(16)           # text / vision / embedding
    provider        = String(32)           # 仅展示用预设标签
    base_url        = String(256)
    model           = String(128)
    api_key_enc     = Text                 # AES-256-GCM（复用 encrypt_key / _at_rest_key）
    api_key_tail    = String(16)           # 仅脱敏展示
    key_fingerprint = String(32)           # sha256(api_key)[:16] —— 判重专用
    priority        = Integer, default 100 # 小 = 优先；同级按 id 顺序（轮询指针见 §4.5）
    enabled         = Boolean, default True
    paid            = Boolean, default False  # 仅 UI 标注"付费模型"，不参与调度过滤
    note            = String(64)           # 备注，如「备用-免费」

    # —— 运行时健康状态（放表里，避免多 worker / 重启丢失）——
    cooldown_until  = DateTime, nullable   # 熔断到期时间；未到期直接跳过
    last_error      = Text, nullable
    last_error_at   = DateTime, nullable
    success_count   = Integer, default 0
    fail_count      = Integer, default 0

    created_at / updated_at
```

**`key_fingerprint` 的必要性**：`crypto.encrypt_obj()` 用随机 nonce，**同一 Key 加密两次结果不同**
（已实测 `a == b → False`）。所以唯一约束**不能**用 `api_key_enc`，必须引入确定性指纹列。

### 4.3 生效解析与回落（零破坏）

新增 `llm_service.resolve_pool(db, user, slot) -> list[dict]`，返回**候选列表**（按 priority, id 排序）：

```
1. 用户池（user_id = user.id, slot, enabled=True）非空  → 用它
2. admin 平台池（user_id = 0, slot, enabled=True）非空   → 用它
3. 两边池都空                                            → 回落现有 resolve_effective 单条逻辑
```

`resolve_effective()` / `resolve_embedding()` **签名与返回值保持不变**（仍返回单条），
池化只新增入口。这样：
- 池空时行为与今天**完全一致**，不会因上线池化而改变任何现有任务的行为
- 存量用户的 `llm_configs` 配置继续生效，无需数据迁移

### 4.5 切换与熔断策略（方案核心，不是「失败就无脑换」）

复用已有的错误归类逻辑 —— 但需**上移**：`_classify_error()` 目前写在 `app/api/llm_config.py:187`（API 层），
池化在 service 层要用，应迁到 `app/services/llm_pool.py`（API 层改为 import），避免反向依赖。

| 错误类型 | 动作 | 理由 |
|---|---|---|
| `rate_limit`(429) / `quota`(402 额度尽) / `server`(5xx) / `network`(超时) | **切下一个**，并给该条记 `cooldown_until = now + N 分钟` | 换服务商就能继续；免费额度是"按日耗尽"的长期状态，不熔断会每次白撞 |
| `auth`(401/403) / 参数错(400) / 模型不存在 | 标记该条不可用，**本轮所有候选一起跳过** | 否则会在每个模型上各撞一次，白花数倍时间 |
| **调用成功但解析出 0 条**（质量类） | **不切换** | 语义是"模型答不出"而非"调用失败"；换一个大概率同样答不出。改由 §1 的关思考 + D 方案的失败上报处理 |

**熔断参数建议**：`rate_limit` 冷却 5 分钟；`quota` 冷却至次日 00:05（按日额度）；`server/network` 冷却 1 分钟。
冷却期内该条直接从候选里过滤；全池都在冷却 → 取冷却最早到期的一条"破格尝试"（避免无限等待）。

**轮询与顺序**：`priority` 升序；同 `priority` 内按 `id`。不做随机化 —— 用户按自己的额度预期排序。

### 4.6 三个必须提前知道的坑

| # | 坑 | 对策 |
|---|---|---|
| 1 | **流式只能在「首字节前」切换** —— 已吐字再换会出现两个模型文本混排 | 沿用现有 `chat_stream` 的 `produced` 标记：仅在未产出任何 delta 时允许换候选 |
| 2 | **超时不能立刻换**：3 个模型各 180s 超时 = 9 分钟白等 | 单模型短超时（建议 60s）+ 整次调用总预算（如 180s），两者同时约束 |
| 3 | **池内混入付费模型 = 静默产生费用** | 老板已确认「费用用户承担」，但 UI 必须**明确标注「付费」徽标** + 池列表显示本次切换留痕（哪个模型失败、切到了谁） |

| 长 URL | 独占一行 + 省略号 | 原先与 Key/统计同行，`break-all` 会把 `compatible-mode/v1` 断在词中间 |

### 10.5 验证期踩到的坑（已定位根因，与代码无关）

**pytest 报一大片 fixture 级 ERROR，先怀疑环境，别急着改代码。**

现象：连续跑全量回归出现 `333 passed / 45 errors`，错误全在 setup 阶段（`SystemExit: 1`），日志里有：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]
{"count":226,"threshold":50,"scope":"turn","targets":[".../ai-testflow/.pytest_tmp"]}
```

根因：`--basetemp=.pytest_tmp` 复用同一目录，**上一轮残留产物数（226）超过沙箱
safe-delete 阈值（50）**，pytest 启动时清理该目录被沙箱 hook 拦截 → 依赖它的 45 个用例
在 setup 阶段全部 ERROR（看起来像"功能炸了"，实际一行代码都没问题）。
换成全新空目录跑 → **0 error**。

规避：`--basetemp=/tmp/aitf_pt_<唯一名>`（每次新建），或跑回归前先清空 `.pytest_tmp`。
判断口诀：**ERROR（setup 阶段）成批出现 + 日志里有 `[safe-delete]` → 环境问题**；
真正的代码回归是 FAILED，且集中在相关模块。
