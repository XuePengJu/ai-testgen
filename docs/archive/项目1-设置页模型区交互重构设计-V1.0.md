# 设置页「模型配置」生效区交互重构设计 V1.0

> 状态：**待评审**（未动代码）
> 范围：`frontend/src/components/settings/EffectiveBar.tsx`、`LLMPoolCard.tsx`、`LLMSlotGroup.tsx`、`SettingsPage.tsx`、`AdminPage.tsx`，后端 `app/api/llm_config.py` 的 `/llm/effective`
> 触发：老板实测反馈 —— "上面和下面有 2 个模型列表，这是不是不对？现在生效应该是多个一起生效吧"

---

## 一、问题全景

| # | 现象 | 影响 |
|---|------|------|
| 1 | 同一个模型名（`agnes-2.0-flash`）在「当前生效模型」和「我的模型配置」各回显一次 | 用户不知道哪个是准的，怀疑界面出错 |
| 2 | 「测连通」有两个入口，测的是同一条候选 | 实测同一模型：上方 28292ms / 下方 507ms，**结论不一致**，互相打脸 |
| 3 | 上方说「文本模型 = 某一条」（唯一生效语义），下方说「模型池 1 条」（集合语义） | 两个模块叙事矛盾，用户自然发问 |
| 4 | 池内 3 条时，上方仍只显示 1 条 + 一个 `来源：pool` 徽标 | **梯队结构完全不可见**，看不出有几条待命、几条冷却 |

**根因**：`EffectiveBar` 诞生于「一个槽位只有一条配置」的时代（M4 期）。池化后它只被改成"回显池内第一条"，**组件的信息架构没有跟着改** —— 于是它成了旧时代的遗产，与池卡对打。

---

## 二、概念澄清：池 ≠ 多个同时生效

这是设计的**前提**，先说准。

| 说法 | 是否成立 | 说明 |
|---|---|---|
| 「池里 5 条，5 个模型同时干活」 | ❌ | 没有实现也不合理 —— 一次生成请求只调一个模型 |
| 「池里 5 条，任一时刻用**第 1 条未冷却**的，失败自动顺延」 | ✅ | 这才是实际行为（`app/services/llm_pool.py` 的 `PoolClient`） |
| 「这 5 条共同组成**一个生效梯队**」 | ✅ | 用户"多条一起生效"的直觉方向对，准确表述是"共同待命" |

调度链路：**一次生成请求 → 按优先级取第 1 条未冷却候选 → 调用 → 失败则该条进冷却并顺延下一条**（同一次请求内完成降级）。冷却策略：限流 5 分钟 / 额度用尽至次日 / 网络与服务异常 1 分钟。全池不可用才回落到单条配置或报错，**不静默失败**。

**因此界面的正确表述是**：这一槽由「池」接管 · 当前优先第 N 条 · 其余 M 条待命 · K 条冷却中。

---

## 三、关键约束（决定了不能简单删掉上面那块）

`EffectiveBar` 是**所有角色可见**（含访客、普通成员）的只读回显；而池卡走 `/llm/pool/{slot}` 个人池端点，**访客无权限**（403）。

> ⚠️ 若直接删掉上方块，访客将完全看不到"当前在用哪个模型"。
> 所以正确解法不是"删一个"，而是**让两块受众与精细度分开**。

---

## 四、方案对比

| 方案 | 做法 | 优点 | 代价 | 适用 |
|---|---|---|---|---|
| **A · 合并** | 删掉上方块，信息全部并入池卡卡头 | 零重复，一屏一信息源 | 访客失去只读视图；跨槽总览消失；embedding 的 mock 警告要搬家 | 只服务配置者本人、无访客场景 |
| **B · 摘要 / 明细分工** ⭐ | 上方降级为**只读调度摘要**（不列全部候选、去掉测连通）；下方池卡承担全部编辑与梯队明细 | 消除重复且**保住访客视图**；符合"摘要—明细"标准信息架构；改动可控 | 模型名仍会出现两次，但一为「结果」一为「结构」，语义不再冲突 | 本项目当前形态（有访客、有 admin/普通成员分层） |
| **C · 运行态监控** | 上方改造成"调度健康度"面板：切换次数、命中分布、冷却倒计时、全槽体检 | 信息零重复，且真正解决新问题（能看出"是不是老在切"） | 需后端加运行态聚合（池表已有 success/fail/cooldown，尚可做）；改动最大 | 后续迭代，可与 B 叠加 |

**推荐 B 先行、C 作为下一迭代**（B 的摘要卡天然是 C 的容器）。

## 五、推荐方案 B 的界面规格

### 5.1 布局分工

```
┌─ 模型调度（只读 · 全角色可见）───────────────┐
│  文本  3 条 · 优先 ①   自定义 · agnes-2.0-flash │
│  图像  1 条 · 优先 ①   自定义 · TM-Kimi-K3      │
│  向量  未启用池        走单条配置 · Ollama·bge-m3│
└──────────────────────────────────────────┘
┌─ 我的模型配置（可编辑）──────────────────────┐
│  默认文本模型  池 3 条 · 可用 2 · 冷却 1  [命中 ①]│
│   ① ▌使用中  ● 自定义 · agnes-2.0-flash   ↑↓  │
│   ②   待命   ● 硅基流动 · Qwen2.5-7B       ↑↓  │
│   ③   冷却中 ● 阿里百炼 · qwen-plus  14:32 后恢复│
│  从上到下依次尝试，第 1 条失败自动换下一条      │
└──────────────────────────────────────────┘
```

**规则**：上方只给「结论」（用谁 + 梯队规模），下方给「结构与操作」（谁在队里、排第几、什么状态）。测连通只保留下方行内一个入口。

### 5.2 上层「模型调度」规格

| 元素 | 内容 | 说明 |
|---|---|---|
| 卡头徽标 | `3 个槽位由模型池接管` / `部分槽位走单条配置` | 一句结论，替代原来的 `来源：user/platform/env` |
| 行（每槽一行） | 槽名（34px 定宽）· `N 条 · 优先 ①`（120px 定宽）· 模型名（省略号） | 三列定宽对齐，模型名超长省略 + `title` 悬浮看全 |
| 未启用池的槽 | 状态位显示 `未启用池`（警告色），右侧显示单条配置的模型名 | 明确告诉用户"这一槽没享受到池容错" |
| 移除 | 三个「测连通」按钮、`来源：xxx` 独立徽标行 | 前者与池卡行内重复，后者并入卡头徽标 |
| 保留 | embedding 的 mock 警告行 | 仍在这一层提示"当前为 mock 向量" |

### 5.3 下层池卡规格（在现有基础上增强）

| 位置 | 现状 | 改为 |
|---|---|---|
| 卡头 | `池 N 条 · 可用 M` + `生效中` | `池 N 条 · 可用 M · 冷却 K` + `命中 ①` |
| 每行前缀 | 序号 + 状态灯 | 序号 + 状态灯 + **状态词**（使用中 / 待命 / 冷却中 / 已停用） |
| 命中行 | 无区别 | 淡紫底 `#F5F4FE` + 左侧 3px 主色竖线（`#7F77DD`→ 实际用项目主色 `#165dff` 的浅色阶），**不靠颜色单独传达**：同时有「使用中」文字徽标 |
| 冷却行 | 仅黄灯 | 淡黄底 + `14:32 后恢复` 倒计时 + `title` 显示 `last_error` |
| 脚注 | 无 | `从上到下依次尝试 —— 第 1 条失败自动换下一条，顺序即优先级` |
| 空态 | `还没有模型池…` | 保留，但补一句"当前走下方单条配置" |

### 5.4 状态定义表

| 状态 | 灯色 | 底色 | 徽标文案 | 判定条件 |
|---|---|---|---|---|
| 使用中 | `#00b42a` | `#F5F4FE` + 左侧竖线 | `使用中` | 该槽第 1 条未冷却且 enabled |
| 待命 | `#00b42a` | 无 | `待命` | enabled 且未冷却，但非第 1 条 |
| 冷却中 | `#EF9F27` | `#FDF8EF` | `HH:MM 后恢复` | `cooldown_until > now`（含 `last_error` 悬浮说明） |
| 已停用 | `#B4B2A9` | 无，整行降透明度 | `已停用` | `enabled = false` |

> 无障碍：**颜色永不单独承载语义** —— 每种状态都配文字，色盲用户可读。

### 5.5 微交互参数

| 元素 | 交互 | 参数 |
|---|---|---|
| 行 hover | 底色淡入 | `background-color .2s ease` |
| 命中行切换 | 竖线 + 底色 | 仅动画 `opacity` / `transform`，`.25s ease-out` |
| ↑↓ 排序点击 | 按压缩放 | `transform: scale(.95)`，`.1s`；悬停 `scale(1.05)`，`.2s` |
| 测试按钮 | 加载态 | 按钮内旋转 loader（`animation: spin 1s linear infinite`，仅 `transform`） |
| 冷却倒计时 | 每分钟刷新 | 不逐秒跳动，避免视觉噪声 |
| 尊重偏好 | — | 全部动效包在 `@media (prefers-reduced-motion: no-preference)` 内 |

### 5.6 色板（沿用项目现有体系，不引入新色）

| 用途 | 色值 | 来源 |
|---|---|---|
| 主色 / 命中标识 | `#165dff` | 现有主色（`.btn-ghost-icon:hover` 已验证使用） |
| 命中行底 | `#F5F4FE` | 主色 5% 淡底 |
| 成功 / 可用 | `#00b42a` | 现有 `.test-ok` |
| 警告 / 冷却 | `#EF9F27`，文字 `#854F0B` | 新增，与 `#d97706` 同族加深保证 4.5:1 |
| 错误 | `#d83931` | 现有 `.test-err` |
| 次要文字 | `#8f959e` | 现有 `.pool-sub` |

**对比度核验**：正文 `#1d2129` on `#FFFFFF` ≈ 15.8:1；`#8f959e` on `#FFFFFF` ≈ 3.4:1（仅用于 12px 辅助信息，**正文不得使用**）；`#854F0B` on `#FDF8EF` ≈ 6.4:1 ✓ 达 AA。

### 5.7 响应式断点

| 断点 | 行为 |

| 档位 | 做法 | 改动 |

### 6.2 一个精度问题（建议一并修）

`pool_first()` 取的是"**首条未冷却**"，即**预期**会命中的候选，不是"上次实际命中"。若上一轮发生过降级，界面显示 `命中 ①` 就与实际不符。

| 选项 | 文案 | 依赖 |
|---|---|---|
| 保守（零改动） | 显示 `优先 ①`（而非"命中"） | 无 |
| 精确 | 池表加 `last_used_at` / `last_hit_at`，显示"最近实际命中 ②" | 加 1 个字段 + 写入点 |

**建议**：本轮先用「优先」，等 P1 时升级为「最近命中」。

## 十、落地记录 V5.1 P1（`pools` 字段，已实施）

**拍板**：方案 B 的补完 —— 摘要卡取数从 **P0（纯前端算）** 升级为 **P1（后端给口径）**。

### 10.1 为什么必须做 P1

§9.2 记的两个偏差同源，都是"前端靠池列表猜"：

- 后端 `source` 只反映 text 槽 → vision / embedding 一律误报「未启用池」；
- 访客无池列表权限（403）→ 只能显示「模型池接管」，显示不出梯队规模。

改由后端每槽下发权威口径，两个偏差一次性消掉。

### 10.2 实际改动

| 文件 | 动作 |
|---|---|
| `services/llm_service.py` | 新增 `resolve_pool_ex()` → `(候选池, "personal" \| "platform" \| None)`；`resolve_pool()` 改为薄封装（**零行为变化**）。来源信息原先只有 API 层一份私有实现，下沉到 service 层统一 |

### 10.3 口径定义（已写进代码注释，避免以后又打架）

| 字段 | 含义 |
|---|---|
| `owner` | 池**归属**（哪一侧在生效），**不等于**"一定有可用候选"：池里条目存在但 Key 全解不开时，owner 仍返回该侧、候选列表为空 |
| `total` | 该槽位**生效池**的全部条数（**含已停用**）—— 与池卡卡头「模型池 N 条」同源，否则上下两处数字会打架 |
| `enabled` | 其中启用的条数 |
| `available` | 启用 + 未冷却 + Key 可解 |
| `cooling` | 候选池中处于冷却期的条数 |
| `hit` | 优先序号（1-based，跳过冷却）；**0 = 无可用候选**（前端显示「N 条 · 全部不可用」而非「优先 ①」） |
| `active` | `available > 0`，即池**真的**在接管 |

### 10.5 实施中踩到的坑

| 坑 | 现象 | 结论 |
|---|---|---|
| 显式点名被 `collect_ignore` 的文件 | `pytest tests/test_embedding_config.py` 直接 collection error | `tests/conftest.py` 的 `collect_ignore` **只在自动收集时生效**；显式传路径会强制收集脚本式 e2e（它们模块级就 `init_db()` + 断言）。跑全量 `tests/` 即可 |
| 非 admin 响应体是密文 | httpx 调 `/llm/effective` 拿到 `{"enc": "..."}`，`.get("pools")` 全 None | `app/core/middleware.py` 对 user / guest **强制加密**（admin 明文）。验证非 admin 视角必须走浏览器，或只断言状态码 |
| 只注入 token 模拟访客 → reload 死循环 | 前端反复刷新，永远等不到「访客」头像 | `client.ts` 的 `cryptoOn` 需要 token **+ encKey + me**；访客态必须让 `AuthContext` 自己静默建立（它同时写 `aitf_token` / `aitf_enc_key` / `aitf_user`） |
| 验证脚本异常退出残留平台池假 Key | 平台池多出一条 `deepseek-chat` 假配置 | `cleanup()` 加平台池兜底扫描（按备注标记），异常路径也能清干净 |

### 10.6 遗留

1. **「最近命中」**：`hit` 仍是"预期会命中"。池表加 `last_used_at` 后可升级为「最近命中 ②」。
2. **方案 C 运行态监控**：`pools` 已是天然容器，下一迭代可加「切换次数 / 命中分布 / 冷却倒计时」。
