## 1. 问题：V5.0 全链路缺「执行期数据安全」这一层

### 1.1 缺口核查（已逐文件核查代码，非推测）

| 检查项 | 现状 | 位置 |
|---|---|---|
| 本轮唯一命名 | **无**。prompt 反而明确要求「输入数据严格按用例的 test_data / steps 填写，不要编造」 | `app/workflow/agents/templates/scripter_case.txt` 第 6 条 |
| 写操作作用域限定 | **无**。没有「只能改自己建的那条」的机制 | 全仓库 |
| 执行后清理 / 回滚 | **无**。conftest 模板只做 storage_state 注入 + 失败截图 hook | `scripter_agent.py` `_CONFTEST_TEMPLATE` |
| 清理台账 | **无**。`mapping.json` 仅「函数名 → 用例ID」名称映射 | `contract-m2-execution.md` 第 1 节 |
| 自愈重跑的数据影响 | **未定义**。M4 自愈 ≤3 轮会重复执行失败用例 | V5.0 第 4 节 |
| run 级标识 | **无**。`ExecutionRun` 无 `run_tag` 字段（`id` 是 uuid 但从未下传脚本） | `app/models/automation.py` 第 73-107 行 |
| 风险登记 | V5.0 第 7 节 8 条风险中，第 7 条只覆盖**密码安全**，无一条覆盖**数据安全** | V5.0 第 7 节 |

### 1.2 真实后果（以 DBERP 进销存为被测系统推演）

| # | 场景 | 后果 |
|---|---|---|
| 1 | 用例 test_data 写死「客户名称=张三」，脚本原样写入 | 第二次执行时要么被唯一性校验阻塞、要么产生第二条同名脏数据 → **用例不具备幂等性，不可重复执行** |
| 2 | 列表中已有 5 条真实「张三」，修改/删除类用例靠文本定位行 | 命中哪一条不确定 → **可能改到或删掉真实业务数据** |
| 3 | 跑完不清理 | 客户表 / 库存表长期累积测试垃圾数据，且**无人知道删哪条** |
| 4 | M4 自愈每轮重跑失败用例 | 脏数据按轮次**倍增**（≤3 轮即最多 3 倍） |
| 5 | 上轮脏数据导致本轮断言失败 | 报告无法区分「产品缺陷」与「脏数据干扰」→ **质量结论不可信** |

### 1.3 为什么必须现在做

- **成本窗口**：M2 执行链路已动工（`auto_runner.py` / `exec_queue.py` / `scripter_agent.py` 均已落地）。此刻加只是「2 个字段 + 1 个模板函数 + 1 个执行阶段」；待 M3 报告结构、M4 自愈收敛、M5 探索 Agent 全部铺开后再回头加，三处都要跟着改，成本数倍。
- **叙事缺口**：本项目的核心定位是「测试专业度」。面试必被问「自动化测试怎么保证不污染业务数据」——按当前方案答不出来。
- **不可回退**：一旦对真实 DBERP 跑过一轮全链路 Demo，残留数据就已产生，事后无法凭报告追溯清理范围。

## 2. 对标做法：LayaPilot 的三个机制

| 机制 | 它的实现 | 可移植性 |
|---|---|---|
| **本轮唯一命名** | 每轮生成 `LayaAuto_{timestamp}_{random}`，所有测试数据由此派生 | 直接可移植 |
| **作用域绑定（owned-row）** | 渲染出的控件带 `scope:'owned-row'`，回放时**只允许**定位「本轮创建的记录」，找不到即报错停止，绝不退化为「取列表第一条」 | 直接可移植，思路最关键 |
| **跑完清理** | 支持的流程中自动清理本轮记录 | 需改造（见 8 节边界声明） |

**不照搬的部分**：LayaPilot 是单机 CLI、单人单轮、无历史留痕需求，清理策略是「跑完即删、删掉即结束」。本项目是在线多用户平台，`ExecutionRun` 是有历史记录的实体，必须**先有可追溯台账、再谈删除**，且清理失败要如实暴露。详见第 8 节。

## 3. 方案设计

### 3.1 三条设计原则

1. **自建 → 自改 → 自删**：任何写操作只能作用于本轮自己创建的数据，不碰存量。
2. **记账优先于清理**：先保证台账完整，删除是台账的下游动作。没有台账的删除是危险的。
3. **清理失败 ≠ 执行失败**：清理异常如实记录为 `partial` 并列出残留，不掩盖、也不污染用例结论。

### 3.2 数据模型变更（`app/models/automation.py`，`ExecutionRun` +2 字段）

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `run_tag` | `String(64)` | `""` | 本轮唯一标识，形如 `AITF_20260923T233012_a3f9`。**幂等**：已存在则复用，M4 自愈不重新生成 |
| `cleanup_json` | `Text` | `None` | 清理台账（结构见下） |

```json
{
  "status": "ok | partial | skipped | unsupported",
  "run_tag": "AITF_20260923T233012_a3f9",
  "created": [{"entity": "客户", "key": "张三_AITF_20260923T233012_a3f9", "case_id": "TC-003"}],
  "deleted": [{"entity": "客户", "key": "张三_AITF_20260923T233012_a3f9"}],
  "leftovers": [{"entity": "客户", "key": "...", "reason": "删除入口未找到"}],
  "started_at": "...", "finished_at": "..."
}
```

不新增表、不新增 run 记录 —— 与 V5.0 第 3.1 节「SQLite / MySQL 双方言零迁移」约定一致。

### 3.3 执行器改动（`app/services/auto_runner.py`）

1. **起跑生成 run_tag**：`f"AITF_{utcnow():%Y%m%dT%H%M%S}_{secrets.token_hex(2)}"`，落库（已存在则复用，保证自愈同轮）。
2. **`_build_env` 注入**：新增 `AITF_RUN_TAG`、`AITF_CLEANUP_LEDGER`（指向 `auto/cleanup_ledger.jsonl`）。凭据注入方式不变。
3. **新增清理阶段**：主 pytest 结束后**无条件**执行（无论主跑成功或失败），独立 subprocess 启动，新开 browser + 复用 `storage_state.json`：

```python
# 伪码：run_execution 主流程末尾
report = _parse_report(...)                     # 现有逻辑不动
cleanup = _run_cleanup(task_dir, auto_path, target, run.run_tag)   # 新增
report["cleanup"] = cleanup                     # report_json 顶层新增段（与 M4 的 heal 段并列）
run.cleanup_json = json.dumps(cleanup, ensure_ascii=False)
_finish(db, run, status="completed", report=report)
```

4. **清理阶段自身超时 / 异常** → `status="partial"` 或 `failed`，写 `leftovers`，**不影响 run 终态判定**（用例结论与数据清理是两件事）。

### 3.4 conftest 模板改动（`scripter_agent.py` `_CONFTEST_TEMPLATE`，仍由代码生成、不经 LLM）

| 新增 | 职责 |
|---|---|
| `run_tag` fixture | 读 `AITF_RUN_TAG` |
| `unique_name(prefix)` | 返回 `f"{prefix}_{RUN_TAG}"`，测试数据一律由此派生 |
| `register_created(entity, key, case_id)` | 追加写 `cleanup_ledger.jsonl`（测试进程内记账，清理阶段读） |
| `register_deleted(entity, key)` | 删除成功后销账，防止清理阶段二次删 |

现有 `base_url` / `storage_state` 注入 / 失败截图 hook **保持不动**（截图命名规则不变，不影响 `_find_screenshot` 的兼容逻辑）。

### 3.5 scripter prompt 硬约定新增 3 条（`templates/scripter_case.txt`）

```
7. 所有测试数据必须由 unique_name("前缀") 派生（如 unique_name("客户")），
   禁止把用例 test_data 里的字面值直接写死；test_data 仅作「字段语义参考」。
8. 修改 / 删除类用例，定位目标行时必须以本轮唯一名过滤；找不到本轮记录时
   调用 pytest.skip("本轮记录不存在")，绝不允许退化为取列表第一条或任意记录。
9. 任何写入（新增 / 修改）成功后，必须立即 register_created(实体, 唯一名, case_id) 记账，
   删除成功后 register_deleted 销账。
```

第 6 条原文（「严格按 test_data 填写」）**改为**：「测试数据按 test_data 的**字段语义**填写，值必须经 `unique_name()` 派生」。

### 3.6 被测系统删除能力适配（`TestTarget` +1 字段）

| 字段 | 取值 | 行为 |
|---|---|---|
| `delete_strategy` | `ui`（默认） | 走页面删除入口 |
| | `api` | 走配置的清理接口（后续扩展位） |
| | `none` | **不尝试清理**，报告显式声明「本目标不支持自动清理，本轮将残留 N 条」——不假装干净 |

### 3.7 与 M4 自愈的衔接

- **复用同一 `run_tag`**（不重新生成）——否则每轮自愈都会产生一批新的孤儿数据。
- 每轮自愈重跑前执行**局部清理**：只清台账中与失败用例相关的半成品记录，避免「上一轮的残缺状态」干扰下一轮诊断。
- 自愈收敛判定**只认断言结果，不看清理结果**（清理属平台卫生，不属产品结论）。

### 3.8 与 M3 前端的衔接

`ExecutionPanel.tsx` 报告视图新增「测试数据」区块：`run_tag` / 本轮创建 N 条 / 已清理 M 条 / 残留 K 条；K>0 时高亮 + 「复制清理清单」按钮。

并发保护：M3 按「字段可选」渲染，M4 落地后字段才有值 —— 沿用 V5.0 第 10 节已有的并发边界约定，避免 M3 被卡。

### 3.9 配置与开关（`app/core/config.py`）

| 配置 | 默认 | 说明 |
|---|---|---|
| `AUTO_DATA_ISOLATION` | `True` | 关闭后回落到现状（固定 test_data 字面值），仅供对照排查 |
| `AUTO_CLEANUP` | `True` | `POST run-auto` 可传 Form 参数 `cleanup: bool = True` 覆盖；传 False 时报告显式标注「本轮未清理」 |
| 只读目标 | 自动降级 | 目标无写操作时 `cleanup.status="skipped"`，run_tag 仍生成供报告标识 |

## 5. 验收标准

| # | 验收项 | 验证方式 |
|---|---|---|
| 1 | 同一任务连跑 2 次，被测系统内本轮记录残留为 **0**，且第二次不被「名称重复」阻塞 | 被测系统侧查询两次执行后的记录数 |
| 2 | 用例 test_data 写死「张三」，实际写入值为 `张三_AITF_...` 形态 | 被测系统侧查询实际值 |
| 3 | 列表中有 5 条同名真实数据时，修改 / 删除类用例只动本轮记录 | 执行后核对其余 4 条未被改动 |
| 4 | 清理失败时 `cleanup.status="partial"`、`leftovers` 非空、run 仍为 `completed` | 构造删除入口缺失场景 |
| 5 | M4 自愈 3 轮后孤儿记录数为 0（证明复用同一 run_tag） | M4 落地后回归 |
| 6 | 现有非 e2e 的 4 步流水线与本功能零耦合 | pytest 全绿回归 |

## 7. 风险与取舍

| 风险 | 应对 |
|---|---|
| 被测系统无删除入口（只归档不删除） | `delete_strategy=none` 降级 + 报告显式声明残留清单，不假装干净 |
| 被测系统不支持自定义命名（编号自动生成） | 退化为「按本轮创建的 ID 记账」，台账结构不变 |
| 清理误删真实数据 | **只按台账里的精确 key 删，绝不做「按前缀模糊删」** —— 多用户 / 并发下模糊删会误伤 |
| 与 M2 并行开发冲突 | 先改契约再动代码（S1 前置），沿用契约文档的裁决机制 |
| 平台自身失败被清理掩盖 | 清理结果独立成段，不参与 run 终态判定（3.1 原则 3） |

### 备选方案对比

| 方案 | 优点 | 代价 | 适用场景 |
|---|---|---|---|
| **A. 台账 + 清理（本方案，推荐）** | 可追溯、清理范围精确、失败可暴露、自愈可复用 | 需 2 字段 + 1 阶段 + 模板改动 | **本项目**（在线多用户、有历史记录、被测系统是真实业务库） |
| B. 跑完即删（LayaPilot 原做法） | 实现最简单 | 无台账不可追溯；中途崩溃即孤儿数据；自愈每轮新增数据 | 单机 CLI、演示型、无历史要求 |
| C. 数据库事务回滚 | 最干净，物理保证零残留 | 需被测系统开放 DB 访问与账号，平台无法假设 | 可完全掌控被测库的团队 |
| D. 独立测试库 / 影子库 | 最彻底，环境级隔离 | 需环境建设与数据同步，超出平台职责范围 | 有专职测试环境建设的团队 |

## 8. 边界声明（不照搬 LayaPilot 的部分）

1. **不自建测试数据准备层**：LayaPilot 只依赖「本轮自建记录」。本项目若用例前置条件要求「系统已存在 XX 状态数据」，属**被测系统侧数据准备**，超出本方案范围，由 target 级配置或人工准备（与 V5.0 第 3.3.1 节的 `checkPrecondition` 思路对齐，可作为后续独立改进点）。
2. **不做「按前缀批量清理」**：LayaPilot 单机单用户可接受，本项目多用户并发下前缀匹配会误伤他人数据。
3. **不改变断言语义**：本方案只解决数据隔离，不放松也不加强任何断言 —— 与 M4「绝不放松断言」的边界一致。
4. **不做跨 run 的残留自动回收**：历史 run 的 `leftovers` 只展示不自动重试，避免误删。
